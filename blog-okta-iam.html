Okta Workflows: Automating IAM Without Writing Traditional Code

Daniel Kamali March 2026 8 min read IAM · Automation · Deriv

Access management at a global fintech company is messier than it sounds. You've got engineers joining, moving between teams, getting access to systems they shouldn't have anymore, and off-boarding processes that rely on someone remembering to click the right buttons. We had all of that. The fix didn't require a development team or a six-month project. It required Okta Workflows, a bit of patience, and learning to think in flow diagrams instead of code.

This post walks through how I built an end-to-end GitHub provisioning workflow triggered entirely from ClickUp task approvals. No custom backend. No scheduled scripts. Just logic connected together with the right API calls at the right points.

The problem we were solving

The old process went something like this: a manager would approve a new joiner's access in a ticket, someone on the IT side would eventually see it, manually extract the GitHub username from the comments, add them to the right org and teams, then update the ticket. It worked until people got busy. Then tickets sat. Then engineers started their first week without the access they needed.

We needed the whole thing automated. Approval in ClickUp triggers provisioning in GitHub, verifies it worked, and updates the ticket status automatically. No human in the loop for the routine case.

How Okta Workflows fits in

Okta Workflows is a no-code automation platform built into Okta. If you're already using Okta for IAM, which most serious companies are, you have access to it. It's not as flexible as writing Python, but for IAM automation it's actually more appropriate because it runs inside your identity layer, has native connectors to the tools you're already using, and doesn't need a server to sit on.

The mental model is similar to tools like Zapier or Make, but with direct access to Okta's user and group management primitives. That matters a lot for what we were building.

The flow structure

The main workflow gets triggered when a ClickUp task moves to an "Approved" status. From there it needs to:

  • Read the task comments to find the GitHub username (engineers submitted these in a standard format ending in -deriv)
  • Look up the correct Okta group based on the team specified in the task
  • Assign the user to that group, which in turn pushes the GitHub org invitation
  • Call the GitHub API to verify the membership actually landed
  • Update the ClickUp task status and add a comment confirming what was done
  • Send a Slack notification to the team channel

Each of those steps sounds straightforward until you start building. The tricky parts are worth explaining.

Extracting the username from comments

ClickUp doesn't give you a structured field for GitHub usernames. Engineers wrote them in free text comments. So I needed to parse a comment string and reliably pull out the username.

Okta Workflows has a Find Pattern card and a Text Segment card. Used together, you can locate a pattern in a string and extract the text at a specific position relative to it. I built this as a helper flow, which is essentially a reusable function in Workflows. The main flow calls the helper, passes in the raw comment text, and gets back just the username.

One thing that tripped me up early: helper flows in Okta Workflows have limited ways to return values. You can't use a For Each loop inside a helper that needs to return a result, because the return card doesn't work cleanly from inside a loop. Structure your logic to avoid that early and you'll save yourself debugging time later.

Dynamic group lookups

We didn't want to hardcode group names into the workflow. If a team is renamed or a new team is added, a hardcoded workflow breaks silently. Instead, the workflow constructs the group name dynamically by concatenating values from the task fields, then calls Okta's List Groups API with that constructed name as the search parameter.

# Group name construction example
team_slug = task.custom_fields["team"].toLowerCase()
group_name = "github-" + team_slug + "-deriv"
# Then: Okta List Groups → filter by name equals group_name

This way, adding a new team just means creating the Okta group with the right naming convention. The workflow figures out the rest.

GitHub verification

Okta pushing a group assignment doesn't immediately mean GitHub membership is active. There's a sync delay. The workflow handles this by calling the GitHub API directly after the Okta assignment, checking whether the user appears as an org member. If they don't appear within a reasonable window, the workflow updates the ClickUp task with a flag rather than silently succeeding.

That flag is important. It means an engineer can see at a glance whether their provisioning completed or needs a follow-up. It also means the IT team isn't flying blind on failures.

The Slack notification

The final step uses Slack Block Kit to send a formatted message to the team channel. Not just "access granted" but the full context: who was provisioned, what team, what GitHub org, and a link back to the original ClickUp task. Block Kit lets you structure this properly so it doesn't look like a bot wrote it.

What I'd do differently

The main thing I'd change is adding more structured logging from the start. Okta Workflows has an execution history, but when you're debugging a failure three weeks after building something, you want richer context than the default output gives you. I've since added comment cards at key decision points that write state to a log task in ClickUp, which makes debugging significantly faster.

I'd also plan for the off-boarding mirror earlier. We built the provisioning flow first, then realised we'd need to build an equivalent de-provisioning flow that ran the same logic in reverse. Building them together from the start would have saved time because several of the helper flows are shared.

The bigger picture

The reason I think this approach is worth writing about is that it shifts who can own IAM automation. You don't need a developer to maintain this. Anyone on an IT or ops team who can think through a process logically can build and maintain Okta Workflows. That changes the ownership model in a meaningful way and means these automations actually get updated when the underlying processes change, rather than sitting as black-box scripts that only one person understands.

For a team operating across multiple time zones and geographies, that resilience matters more than technical elegance.
